# bluemap-worldscan

A [BlueMap](https://github.com/BlueMap-Minecraft/BlueMap) addon that shows the structures of a
Minecraft world on the map, one toggleable layer per kind: villages, ocean monuments, woodland
mansions, trial chambers, end city ships and the rest. Each marker has a popup with the name, the
block coordinates and a `/tp` command you can copy.

Tools like Chunkbase work out structures from the world seed. That is wrong in an old world: the
chunks near spawn were generated by older Minecraft versions, and areas that were pruned and
generated again have different structures than the seed says. This addon does not use the seed. It
reads the region files of the world and takes the structure starts that are stored in the chunks,
so a marker is where the structure really is.

It is one jar, with no Minecraft or loader dependency. It works as a BlueMap addon in the server
mods and plugins and in the BlueMap CLI. It is built for BlueMap 5.29 (BlueMap API 2.8.2) and
needs the Java version BlueMap 5.29 runs on, Java 25.

Biome layers are not part of this version. The scan already records which biomes each chunk holds
and the `biomes` settings are read from the config, but they change nothing yet.

## What it does

- **Reads region files, read-only.** It opens them for reading, takes no locks and never writes
  into the world folder. The game server can keep running. A chunk that is caught while the game
  writes it is not taken, and is read again on the next scan.
- **Reads chunks from Minecraft 1.13 to 26.3.** That covers the chunk layouts before and after
  1.18. Structures saved by older versions show under the ids the current game gives them (an old
  `Village` start is a village). Chunks older than 1.13 are counted, not read (see
  [Old chunks](#old-chunks)).
- **Scans only what changed.** The first scan reads every chunk. After that each scan reads the
  chunks that are new or whose save time changed. Chunks that were pruned and region files that
  were deleted drop out of the result.
- **Scans each time BlueMap enables**: a server start, `/bluemap reload`, a BlueMap CLI render run.
  There is no periodic rescan.
- **Stores the finished layers once per map.** After a complete pass over a world, the scanning
  instance stores the layers in the asset storage of each map of that world. Every BlueMap instance
  that uses that storage and runs the addon shows the same layers from it.

The layers appear after the first complete pass. On a large world that takes hours (see
[Performance](#performance)), and nothing is stored before the pass is done.

## Install

Use the same addon version on every BlueMap instance that uses the same map storage.

1. On an instance that must not scan, create the config first. Put
   `<bluemap config>/bluemap-worldscan/config.json` in place with this content:

   ```json
   { "scan": false }
   ```

   Do this before the jar goes in. A missing config is written with `scan` on, and the first start
   would begin a full scan, in the game server's JVM if that is where BlueMap runs, and as a
   second scanner on the storage.
2. Put `bluemap-worldscan-<version>.jar` in `<bluemap config>/packs/`.
3. Start BlueMap.

`<bluemap config>` is BlueMap's config folder: `config/bluemap/` for the Fabric mod, `/app/config/`
in the BlueMap CLI container. The addon keeps its own files in `bluemap-worldscan/` next to
`packs/`, not inside it, because BlueMap treats every file in `packs/` as a resource pack.

**To update, replace the jar. Never leave two versions in `packs/`.** BlueMap fails to start when
two jars have the same addon id. Then restart the whole server or CLI process: `/bluemap reload`
does not load a new version of an addon that is already loaded.

### The addon folder

| Path | What it is |
|---|---|
| `config.json` | The settings below. Written with the defaults when it is missing. |
| `reset` | An empty file you create to make the next scan start from zero. It is deleted after. |
| `scanner-id` | A random id written on first use. It tells this scanner from another one. |
| `state/` | The scan state: one file per world, with the save time of every chunk and what was found in it. |
| `client-jar/` | The Minecraft client jar the layer icons are made from. |

## The three setups

Exactly one instance per map storage should scan. The other instances show what it stored. The
manifest names the scanner. A scanner that finds another scanner's id in a map's manifest logs a
warning.

| Setup | What the addon does |
|---|---|
| BlueMap as server mod or plugin only, `scan` on | On enable it shows the stored layers, then scans on its own thread inside the game JVM. At the end of each world's pass it stores and shows the new layers. BlueMap's webserver serves the layers, and the plugin's own save every 10 minutes keeps them in storage. On disable (server stop, reload) it cancels the scan and waits at most 5 seconds. The scan state checkpoint stays. |
| BlueMap CLI only, render run (`-r` or `-u`, with or without `-w`), `scan` on | On enable, during the render run, it shows the stored layers, then scans. When a render run without `-u` finishes, the CLI disables BlueMap. The addon waits there until the scan is done, so the CLI's final save stores the new layers, and `-w` then serves them. If the process is stopped (Ctrl-C, `docker stop`), the scan is cancelled and that wait ends after the current chunk. Stopping is also the only way a watch-mode `-u` run ends. A CLI run with `-w` only never starts the addon and serves the layers as last saved by a render run or a plugin. |
| Both on one storage: the plugin with `scan` off, the CLI container with `-r -w` and `scan` on | The container scans and serves the layers on its own port. The plugin shows the stored layers when it starts and picks up each new generation within `refreshMinutes`. Both end up with the same layers. The reverse also works: the plugin scans, and the CLI has `scan` off. The CLI keeps checking after its render run ends, so its `-w` follows new generations. |

A few consequences:

- A webserver-only CLI or a static web host shows the layers as last saved by an instance that runs
  the addon.
- A CLI run with `-m` updates only the maps it loads.
- **`bluemap-cli --markers` wipes the layers from storage.** It writes only the marker sets of the
  map configs to storage, so the worldscan layers are gone from the stored marker state, and from
  a `-w`-only or static map, until an instance that runs the addon saves again. A plugin does that
  every 10 minutes, and a CLI render run does it at its end.
- The scanning instance's config decides what the layers hold. The display settings below are read
  there only.

## Configuration

`config.json` is read each time BlueMap enables. Change it, then restart BlueMap or run
`/bluemap reload`. Keys you leave out keep their default, so `{ "scan": false }` is a complete file.

```json
{
  "scan": true,
  "maxChunksPerSecond": 500,
  "refreshMinutes": 5,
  "structures": {
    "disabledLayers": ["mineshaft", "buried_treasure"]
  },
  "biomes": {
    "enabled": true,
    "cellSizeChunks": 4,
    "disabled": []
  }
}
```

| Key | Default | Meaning |
|---|---|---|
| `scan` | `true` | Whether this instance scans. Every instance shows the stored layers either way. |
| `maxChunksPerSecond` | `500` | The most chunks a scan reads per second. At least 1. Scanning instance only. |
| `refreshMinutes` | `5` | How often an instance with `scan` off looks for a new generation of layers. `0` turns it off. An instance that scans does not use it. |
| `structures.disabledLayers` | `["mineshaft", "buried_treasure"]` | Layer ids that are not built. Scanning instance only. See the table below. |
| `biomes.enabled`, `biomes.cellSizeChunks`, `biomes.disabled` | `true`, `4`, `[]` | Settings for biome layers. They have no effect in this version. |

A config that cannot be read, or that holds an impossible value (such as `maxChunksPerSecond` below
1), logs one line and gives the defaults with `scan` off. A typo never starts a scan nobody asked
for.

To start over, create an empty file named `reset` in the addon folder. At the next enable, an
instance with `scan` on deletes the stored scan state and the `reset` file, and scans every chunk.

### Layers

Each layer is a marker set with the id `worldscan-structure-<layer id>` and shows in BlueMap's
sidebar. Layers marked "off" start switched off in the sidebar. Layers marked "not built" are in
`structures.disabledLayers` by default and have no markers until you remove them from it.

| Layer id | Sidebar name | Default |
|---|---|---|
| `abandoned_camp` | Abandoned camp | on |
| `ancient_city` | Ancient city | on |
| `bastion_remnant` | Bastion remnant | on |
| `buried_treasure` | Buried treasure | not built (off when built) |
| `desert_pyramid` | Desert pyramid | on |
| `end_city` | End city | on |
| `end_city_ship` | End city ship | on |
| `igloo` | Igloo | on |
| `jungle_pyramid` | Jungle pyramid | on |
| `mineshaft` | Mineshaft | not built (off when built) |
| `fortress` | Nether fortress | on |
| `nether_fossil` | Nether fossil | off |
| `monument` | Ocean monument | on |
| `ocean_ruin` | Ocean ruin | off |
| `pillager_outpost` | Pillager outpost | on |
| `ruined_portal` | Ruined portal | off |
| `shipwreck` | Shipwreck | off |
| `stronghold` | Stronghold | on |
| `swamp_hut` | Swamp hut | on |
| `trail_ruins` | Trail ruins | on |
| `trial_chambers` | Trial chambers | on |
| `village` | Village | on |
| `mansion` | Woodland mansion | on |

A layer holds all variants of its kind: `village` has the plains, desert, savanna, snowy and taiga
villages, `mineshaft` has the badlands mineshaft, `ruined_portal` has the nether, ocean and other
portals, and `ocean_ruin` and `shipwreck` hold their variants too.

A structure id the addon does not know (from a datapack, or from a Minecraft version newer than
26.3) gets a layer of its own, named from the id: `some_pack:big_tower` becomes "Big tower
(some_pack)" with the layer id `some_pack_big_tower`. It has no icon and is on by default. The
unknown id is also listed in the log after the scan.

The end city ship layer has a marker at the ship itself, not at the end city.

### Markers

A marker sits at the middle of the structure's bounding box, on top of it. Its popup shows the
layer name, `x y z` and `/tp @s x y z`. A buried structure can be below the surface, so the `/tp`
target may be inside rock: use spectator mode to get there.

Most layers show from a distance of 5000 blocks. The dense layers (buried treasure, mineshaft,
nether fossil, ocean ruin, ruined portal, shipwreck) and trial chambers show once you are closer
than 1000 blocks.

### Icons

The icons come from the vanilla textures in the Minecraft client jar. No Mojang asset is bundled.
The scanning instance downloads the client jar of the newest release from Mojang's version
manifest, checks its SHA-1 and keeps it in `client-jar/`. It only follows https URLs under
`mojang.com` and refuses a jar over 200 MB. It stores one small icon per layer in the asset
storage of each map. If the download fails and there is no kept jar, the layers have no icons and
BlueMap draws its default marker. Instances that do not scan download nothing.

## What every browser has to load

BlueMap serves all marker sets of a map in one file, `live/markers.json`. The web app fetches it
once and then every 10 seconds while no SSE connection is open. SSE is the event stream BlueMap's
webserver offers. Behind a proxy that buffers it, SSE does not work, and then every open browser
downloads the whole file every 10 seconds. With SSE, an instance serialises its marker sets at most
every 10 seconds while a browser is connected, and sends them only when they changed. When markers
are served from storage and the storage compression is not one the browser accepts, they are
compressed again on each request.

Hidden layers count. A layer that starts switched off still has its markers in the file. The way
to make the file smaller is to build fewer markers, with `structures.disabledLayers`. The
`biomes.cellSizeChunks` and `biomes.disabled` keys will be the levers for biome layers, once those
exist.

A marker takes about 500 bytes in `live/markers.json`, about 190 of them the popup. Measured on one
large overworld (3,617,924 chunks, 4,262 region files):

| Layers | Markers | `live/markers.json` |
|---|---|---|
| Defaults (`mineshaft` and `buried_treasure` not built) | 11,577 | 5,799,677 bytes |
| Only `mineshaft` not built | 12,543 | 6,294,603 bytes |
| Every layer | 26,765 | 13,332,708 bytes |

In that world mineshafts alone were more than half of all structures (14,222 of 26,765), and they
are why `mineshaft` is not built by default. `buried_treasure` is not built either, to keep the file
smaller. If your world is large and the web app is slow to load, look at this number first.

When the uncompressed layers of a map pass 8 MiB, the scanner logs a warning with the settings that
make them smaller.

## Performance

- The scan runs on one thread called `bluemap-worldscan`. It is a daemon thread at the lowest Java
  priority. **Java thread priorities have no effect on Linux** (HotSpot ignores them by default),
  so on Linux `maxChunksPerSecond` is what limits the CPU and disk use of a scan. Lower it if the
  game server's tick time rises during the first scan.
- The rate cap counts only chunks that are read. At the default of 500 chunks per second, a first
  scan of 4.2 million chunks (4,178,459 chunks over three dimensions) takes about 2.3 hours. Later
  scans read only changed chunks.
- The scan state is saved to the addon folder every 100 regions, so a scan that is cancelled keeps
  the regions it finished and the next scan continues from them. Layers are stored only after a
  complete pass, so every stored generation is complete.
- When a scan is cancelled (server stop, reload), the layers that were stored before stay as they
  are.

## What the log shows

The addon logs through the Java logger with the prefix `[bluemap-worldscan]`. The lines reach
standard error on every platform. Look for:

- `scanning world <id> (<dimension folder>)` when a world's pass starts.
- `scanned <dimension folder>: read N, unchanged N, failed N, wrong position N, changed during
  read N, pre-1.13 N, unsupported compression N; DataVersions ...` at the end of each world's
  pass. The DataVersions are counted in six buckets: `< 1466`, `1466-2199`, `2200-2831`,
  `2832-2843`, `2844-2969` and `>= 2970`. At debug level every distinct DataVersion is listed
  too. Structure and biome ids the addon does not know are listed at the end of the line: the first
  20 of each kind, then how many more.
- `stored generation G of the layers of map <id> (N markers)` when new layers were stored, or
  `the layers of map <id> are unchanged`.
- `showing generation G of map <id> (N layers)` when an instance puts a stored generation on its
  map.

If the dimension folder of a world has no `region` folder (a wrong path, an unmounted volume), the
scan logs a warning, reads nothing and stores nothing, so it cannot wipe your layers.

## Old chunks

Chunks saved before Minecraft 1.13 are counted in the `pre-1.13` number of the scan line and
nothing else is read from them. BlueMap 5.29 cannot read them either. The `data/*.dat` structure
files of those versions are not read.

To convert them, run the Minecraft server with `--forceUpgrade` (back up the world first). It
rewrites old chunks in the current format and moves the old structure data into the chunks. A
chunk's save time decides whether it is read again, so afterwards create the `reset` file to be
sure the scan reads every chunk again.

## Privacy

BlueMap's webserver serves a map's asset storage to anyone who can reach the map. The addon puts
three things there, per map:

- `bluemap-worldscan-layers.json.gz`, the layers: the markers of the layers that are built, with
  their positions and popups. This is what `live/markers.json` shows anyway.
- `bluemap-worldscan-manifest.json`: the format version, the generation number, the scanner id (a
  random UUID), the addon version and a SHA-1 of the layers.
- `bluemap-worldscan-icon-<layer>-<hash>.png`, the icons.

Anyone who can open the map can see the structure positions of the layers that are built. If that
is a problem for a layer, put it in `structures.disabledLayers`.

These stay with the scanning instance, in its addon folder, and are never put in the storage: the
scan state (the save time of every chunk, the structures of layers you disabled, the biomes of each
chunk), the `scanner-id` file, the config and the client jar. Instances that do not scan read no
world files and download nothing.

## When a new release is needed

You need a new release of the addon when:

- BlueMap changes its API in a way that breaks the addon,
- Minecraft changes the chunk format so the addon cannot read structure starts any more, or
- a new Minecraft version adds structures. Until then they are shown in a layer named from their id,
  with no icon, and listed as unknown in the log.

A stored layers file or manifest in a format a running instance does not know is left alone: the
instance keeps the layers it shows and logs `update bluemap-worldscan on this instance`. A scanning
instance that finds such files in a map's storage stores nothing for that map and logs a warning,
so an old addon never replaces the layers of a newer one.

## Build

```
./gradlew build
```

needs Java 25. The addon jar is `build/libs/bluemap-worldscan-<version>.jar`. The other jar in that
folder, `-plain`, is the build without its libraries and is not for use.

Pushing a tag that starts with `v` runs `.github/workflows/release.yml`. It builds the jar, checks
it and attaches it to a GitHub release.
