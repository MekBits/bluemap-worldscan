# bluemap-worldscan

A [BlueMap](https://github.com/BlueMap-Minecraft/BlueMap) addon that shows the structures of a
Minecraft world on the map, one toggleable layer per kind: villages, ocean monuments, woodland
mansions, trial chambers, end city ships and the rest. Each marker has a popup with the name and the
block coordinates. Every biome is a layer too, which shows the areas where the biome occurs, caves
included.

Tools like Chunkbase work out structures from the world seed. That is wrong in an old world: the
chunks near spawn were generated by older Minecraft versions, and areas that were pruned and
generated again have different structures than the seed says. This addon does not use the seed. It
reads the region files of the world and takes the structure starts and biomes that are stored in
the chunks, so a marker is where the structure really is and a biome area is where the biome really
is.

It is one jar, with no Minecraft or loader dependency. It works as a BlueMap addon in the server
mods and plugins and in the BlueMap CLI. It is built for BlueMap 5.29 (BlueMap API 2.8.2) and
needs the Java version BlueMap 5.29 runs on, Java 25.

## What it does

- **Reads region files, read-only.** It opens them for reading, takes no locks and never writes
  into the world folder. The game server can keep running. A chunk that is caught while the game
  writes it is not taken, and is read again on the next scan.
- **Reads chunks from Minecraft 1.13 to 26.3.** That covers the chunk layouts before and after
  1.18. Structures and biomes saved by older versions show under the ids the current game gives
  them (an old `Village` start is a village, an old `mountains` biome is `windswept_hills`). Chunks
  older than 1.13 are counted, not read (see [Old chunks](#old-chunks)).
- **Scans only what changed.** The first scan reads every chunk. After that each scan reads the
  chunks that are new or whose save time changed. Chunks that were pruned and region files that
  were deleted drop out of the result.
- **Scans each time BlueMap enables**: a server start, `/bluemap reload`, a BlueMap CLI render run.
  There is no periodic rescan.
- **Stores the finished layers once per map.** After a complete pass over a world, the scanning
  instance stores the layers in the asset storage of each map of that world. Every BlueMap instance
  that uses that storage and runs the addon shows the same layers from it.
- **Covers the whole world.** The layers hold every structure found in the world, and the biome
  layers outline every chunk whose biomes have been generated, also when a map's render area or mask
  is limited: the addon does not read BlueMap's render bounds.

The layers appear after the first complete pass. On a large world that takes hours (see
[Performance](#performance)), and nothing is stored before the pass is done.

## Install

Use the same addon version on every BlueMap instance that uses the same map storage, and upgrade
all of them together. Release 1.0.0 cannot read the layers file that 1.1.0 stores (format version
2). An instance still on 1.0.0 keeps showing the sets it has and logs
`update bluemap-worldscan on this instance`, until it restarts or reloads; then it shows no
worldscan layers. A webserver-only CLI (`-w`) that is fed by such an instance shows none either.
Release 1.1.0 reads the layers that 1.0.0 stored, and replaces them after its first scan.

**Upgrading from 1.0.0.** Release 1.0.0 wrote its whole default settings into the `config.json` it
created, so that file holds `"cellSizeChunks": 4`. Release 1.1.0 keeps the value from the file, and
4 chunks per cell is a lot of corners on a large overworld: the measured one takes about 18 MB in
`live/markers.json`. After upgrading, set `biomes.cellSizeChunks` to 16, or delete the `biomes`
block from the file to get the default.

1. On an instance that must not scan, create the config first. Put
   `<bluemap config>/bluemap-worldscan/config.json` in place with this content:

   ```json
   { "scan": false }
   ```

   Do this before the jar goes in. A missing config is written with `scan` on, and the first start
   would begin a full scan, in the game server's JVM if that is where BlueMap runs, and as a
   second scanner on the storage.
2. Put `bluemap-worldscan-<version>.jar` in `<bluemap config>/packs/`.
3. Start BlueMap.

`<bluemap config>` is BlueMap's config folder: `config/bluemap/` for the Fabric, Forge and NeoForge
mods, `plugins/BlueMap/` for the Paper and Spigot plugin, `/app/config/` in the BlueMap CLI
container. The addon keeps its own files in `bluemap-worldscan/` next to `packs/`, not inside it,
because BlueMap treats every file in `packs/` as a resource pack.

**To update, replace the jar. Never leave two versions in `packs/`.** BlueMap fails to start when
two jars have the same addon id. Then restart the whole server or CLI process: `/bluemap reload`
does not load a new version of an addon that is already loaded.

### The addon folder

| Path | What it is |
|---|---|
| `config.json` | The settings below. Written with the defaults when it is missing. |
| `reset` | An empty file you create to make the next scan start from zero. It is deleted after. |
| `scanner-id` | A random id written on first use. It tells this scanner from another one. |
| `state/` | The scan state: one file per world, with the save time of every chunk and what was found in it. |
| `client-jar/` | The Minecraft client jar the layer icons are made from. |

## The three setups

Exactly one instance per map storage should scan. The other instances show what it stored. The
manifest names the scanner. A scanner that finds another scanner's id in a map's manifest logs a
warning. When it then stores the same layers, they are stored again under its own id, so the
warning shows once when the scanning role moves from one instance to another, and keeps showing
only while two instances really alternate.

| Setup | What the addon does |
|---|---|
| BlueMap as server mod or plugin only, `scan` on | On enable it shows the stored layers, then scans on its own thread inside the game JVM. At the end of each world's pass it stores and shows the new layers. BlueMap's webserver serves the layers, and the plugin's own save every 10 minutes keeps them in storage. On disable (server stop, reload) it cancels the scan and waits at most 5 seconds. The scan state checkpoint stays. |
| BlueMap CLI only, render run (`-r` or `-u`, with or without `-w`), `scan` on | On enable, during the render run, it shows the stored layers, then scans. When a render run without `-u` finishes, the CLI disables BlueMap. The addon waits there until the scan is done, so the CLI's final save stores the new layers, and `-w` then serves them. If the process is stopped (Ctrl-C, `docker stop`), the scan is cancelled and that wait ends after the current chunk. Stopping is also the only way a watch-mode `-u` run ends. A CLI run with `-w` only never starts the addon and serves the layers as last saved by a render run or a plugin. |
| Both on one storage: the plugin with `scan` off, the CLI container with `-r -w` and `scan` on | The container scans and serves the layers on its own port. The plugin shows the stored layers when it starts and picks up each new generation within `refreshMinutes`. Both end up with the same layers. The reverse also works: the plugin scans, and the CLI has `scan` off. The CLI keeps checking after its render run ends, so its `-w` follows new generations. |

A few consequences:

- A webserver-only CLI or a static web host shows the layers as last saved by an instance that runs
  the addon.
- A CLI run with `-m` updates only the maps it loads.
- **`bluemap-cli --markers` wipes the layers from storage.** It writes only the marker sets of the
  map configs to storage, so the worldscan layers are gone from the stored marker state, and from
  a `-w`-only or static map, until an instance that runs the addon saves again. A plugin does that
  every 10 minutes, and a CLI render run every 2 minutes and at its end.
- The scanning instance's config decides what the layers hold. The display settings below are read
  there only.

## Configuration

`config.json` is read each time BlueMap enables. Change it, then restart BlueMap or run
`/bluemap reload`. Keys you leave out keep their default, so `{ "scan": false }` is a complete file.

```json
{
  "scan": true,
  "maxChunksPerSecond": 500,
  "scanThreads": 1,
  "refreshMinutes": 5,
  "structures": {
    "disabledLayers": ["mineshaft", "buried_treasure"]
  },
  "biomes": {
    "enabled": true,
    "cellSizeChunks": 16,
    "disabled": []
  }
}
```

| Key | Default | Meaning |
|---|---|---|
| `scan` | `true` | Whether this instance scans. Every instance shows the stored layers either way. |
| `maxChunksPerSecond` | `500` | The most chunks a scan reads per second, over all its threads. `0` is no cap. Scanning instance only. |
| `scanThreads` | `1` | How many region files a scan reads at the same time, from 1 to 64. More than 1 is for an instance that has the CPU to itself, such as the BlueMap CLI container; see [Performance](#performance). Scanning instance only. |
| `refreshMinutes` | `5` | How often an instance with `scan` off looks for a new generation of layers. `0` turns it off. An instance that scans does not use it. |
| `structures.disabledLayers` | `["mineshaft", "buried_treasure"]` | Layer ids that are not built. Scanning instance only. See the table below. |
| `biomes.enabled` | `true` | Whether biome layers are built. `false` builds none. Scanning instance only. |
| `biomes.cellSizeChunks` | `16` | The resolution of the biome areas: the side of a cell in chunks. From 1 to 1,875,000 (the world border, 30,000,000 blocks, in chunks). A larger cell gives a coarser, smaller layer. Scanning instance only. See [Biomes](#biomes). |
| `biomes.disabled` | `[]` | Biomes that are not built, as ids with or without the namespace: `["plains", "minecraft:river", "some_pack:crystal_caves"]`. Scanning instance only. |

A config that cannot be read, or that holds an impossible value (such as a negative
`maxChunksPerSecond`, or a `biomes.cellSizeChunks` outside its range), logs one line and gives the
defaults with `scan` off. A typo never starts a scan nobody asked for.

To start over, create an empty file named `reset` in the addon folder. At the next enable, an
instance with `scan` on deletes the stored scan state and the `reset` file, and scans every chunk.

### Layers

Each layer is a marker set with the id `worldscan-structure-<layer id>` and shows in BlueMap's
sidebar. Layers marked "off" start switched off in the sidebar. Layers marked "not built" are in
`structures.disabledLayers` by default and have no markers until you remove them from it.

| Layer id | Sidebar name | Default |
|---|---|---|
| `abandoned_camp` | Abandoned camp | on |
| `ancient_city` | Ancient city | on |
| `bastion_remnant` | Bastion remnant | on |
| `buried_treasure` | Buried treasure | not built (off when built) |
| `desert_pyramid` | Desert pyramid | on |
| `end_city` | End city | on |
| `end_city_ship` | End city ship | on |
| `igloo` | Igloo | on |
| `jungle_pyramid` | Jungle pyramid | on |
| `mineshaft` | Mineshaft | not built (off when built) |
| `fortress` | Nether fortress | on |
| `nether_fossil` | Nether fossil | off |
| `monument` | Ocean monument | on |
| `ocean_ruin` | Ocean ruin | off |
| `pillager_outpost` | Pillager outpost | on |
| `ruined_portal` | Ruined portal | off |
| `shipwreck` | Shipwreck | off |
| `stronghold` | Stronghold | on |
| `swamp_hut` | Swamp hut | on |
| `trail_ruins` | Trail ruins | on |
| `trial_chambers` | Trial chambers | on |
| `village` | Village | on |
| `mansion` | Woodland mansion | on |

A layer holds all variants of its kind: `village` has the plains, desert, savanna, snowy and taiga
villages, `mineshaft` has the badlands mineshaft, `ruined_portal` has the nether, ocean and other
portals, and `ocean_ruin` and `shipwreck` hold their variants too.

A structure id the addon does not know (from a datapack, or from a Minecraft version newer than
26.3) gets a layer of its own, named from the id: `some_pack:big_tower` becomes "Big tower
(some_pack)" with the layer id `some_pack_big_tower`. It has no icon and is on by default. The
unknown id is also listed in the log after the scan.

The end city ship layer has a marker at the ship itself, not at the end city.

### Biomes

Each biome found in the world is a marker set with the id `worldscan-biome-<namespace>-<path>`
(`worldscan-biome-minecraft-lush_caves`) and the sidebar name "Biome: " followed by the English
name of the biome, from the language file of the Minecraft client jar. A biome the file does not
name (a datapack's, or one newer than the client jar) is named from its id, as "Crystal caves
(some_pack)". Every biome layer starts switched off.

- A layer shows the areas where the biome occurs **at any height**, so cave biomes such as Lush
  Caves and Deep Dark show as well. It is not a map of the surface biome.
- The world is cut into square cells of `biomes.cellSizeChunks` chunks (the default 16 is 256
  blocks). A cell belongs to a biome when any chunk in it has the biome, so an area reaches up to a
  cell beyond the real edge of the biome. Cells that touch are joined into one area, with holes
  where there are any.
- A world gets layers for at most 512 biomes (vanilla has about 65). Above that the first 512 by id
  get one, and a warning says how many were left out. Biomes in `biomes.disabled` do not count.
- Two limits protect the game server's memory and the browser. The addon holds one entry for every
  biome and cell pair before it traces the outlines, and builds no biome layers for a world with
  more than 2,000,000 pairs (16 to 32 bytes a pair, 48 for a moment while a set grows, plus the
  outlines of the one biome being traced). After the areas are worked out, it
  estimates their size in `live/markers.json` (365 bytes an area and 21 a corner), and builds no
  biome layers for a world whose areas come to more than 100,000,000 bytes. In both cases a warning
  names `biomes.cellSizeChunks`, and a larger cell fixes it. The structure layers are not affected.
  The measured overworld has 6,301,195 pairs at 1 chunk per cell, which is over the first limit, and
  1,890,859 at 2, 617,761 at 4 and 222,876 at 8, which are under it. A world whose region files lie
  more than about 2 billion cells apart (far beyond the world border) gets no biome layers either,
  with a warning that names `biomes.cellSizeChunks`.
- The biome layers outline every chunk whose biomes have been generated, at the resolution of the
  cell, also outside a map's render bounds or mask. With small cells that is close to the per-chunk
  biome data of the world, and it is shown to everyone who can open the map. `biomes.disabled` hides
  single biomes; only `biomes.enabled` `false` removes the footprint.
- Only chunks whose biomes have been generated count. A chunk at the edge of the generated land
  that is still half built does not show as plains.
- An area is drawn at height 63, through the terrain, in a colour of the biome at 45 % opacity with
  a line in the same colour. The colours are fixed for the 67 biomes of Minecraft 26.3 (blues for
  the oceans, yellow for beaches and deserts, red for the nether, purple for the end); a biome that
  is not in the table gets a colour worked out from its id. Areas are not listed in the sidebar,
  only the layer is.
- The Nether and End maps show the biomes of their own dimensions.
- Biomes saved by older Minecraft versions show under their current names.

The biome layers add to `live/markers.json`, which every browser loads: see the next section.

### Markers

A marker sits at the middle of the structure's bounding box, on top of it. Its popup shows the
layer name and `x y z`. The height is the top of the box, so for a buried structure the
coordinates can be inside rock: use spectator mode to get there.

Most layers show from a distance of 5000 blocks. The dense layers (buried treasure, mineshaft,
nether fossil, ocean ruin, ruined portal, shipwreck) and trial chambers show once you are closer
than 1000 blocks.

### Icons

The icons come from the vanilla textures in the Minecraft client jar. No Mojang asset is bundled.
Each texture is cropped to its picture, scaled up by a whole factor to at most 32 pixels and
outlined in black and white, so the icon stands out on land and water when the map is zoomed out.
The scanning instance downloads the client jar of the newest release from Mojang's version
manifest, checks its SHA-1 and keeps it in `client-jar/`. It only follows https URLs under
`mojang.com` and refuses a jar over 200 MB. It stores one small icon per layer in the asset
storage of each map. If the download fails and there is no kept jar, the layers have no icons and
BlueMap draws its default marker. Instances that do not scan download nothing.

## What every browser has to load

BlueMap serves all marker sets of a map in one file, `live/markers.json`. The web app fetches it
once and then every 10 seconds while no SSE connection is open. SSE is the event stream BlueMap's
webserver offers. Behind a proxy that buffers it, SSE does not work, and then every open browser
downloads the whole file every 10 seconds. With SSE, an instance serialises its marker sets at most
every 10 seconds while a browser is connected, and sends them only when they changed. When markers
are served from storage and the storage compression is not one the browser accepts, they are
compressed again on each request.

Hidden layers count. A layer that starts switched off still has its markers in the file. The ways
to make the file smaller are to build fewer markers, with `structures.disabledLayers` and
`biomes.disabled`, to switch biome layers off with `biomes.enabled`, or to give the biome areas
fewer corners with a larger `biomes.cellSizeChunks`.

A marker takes about 435 bytes in `live/markers.json`, about 125 of them the popup. Measured on one
large overworld (3,617,924 chunks, 4,262 region files), structure layers only, when the popup also
held a `/tp` command, which took about 50 bytes more per marker:

| Layers | Markers | `live/markers.json` |
|---|---|---|
| Defaults (`mineshaft` and `buried_treasure` not built) | 11,577 | 5,614,445 bytes |
| Only `mineshaft` not built | 12,543 | 6,093,915 bytes |
| Every layer | 26,765 | 12,904,468 bytes |

In that world mineshafts alone were more than half of all structures (14,222 of 26,765), and they
are why `mineshaft` is not built by default. `buried_treasure` is not built either, to keep the file
smaller. If your world is large and the web app is slow to load, look at this number first.

A biome area takes about 365 bytes and 21 bytes for each corner of its outline (fitted to the
measurements below, within 1 %). Every biome layer is in the file whether it is
shown or not.

With the default settings (and the popup with `/tp`) that world gave a `live/markers.json` of
9,162,685 bytes: the default structure layers (5,614,445 bytes) and the biome layers at 16 chunks per
cell (3,548,241 bytes). The same overworld, which has 55 biomes, at other cell sizes:

| `biomes.cellSizeChunks` | Biome areas | Corners | Biomes in `live/markers.json` | Whole file |
|---|---|---|---|---|
| 2 | 23,037 | 680,728 | 22,871,227 bytes | 28,485,671 bytes |
| 4 | 16,469 | 321,852 | 12,827,634 bytes | 18,442,078 bytes |
| 8 | 10,241 | 150,996 | 6,937,932 bytes | 12,552,376 bytes |
| 12 | 7,383 | 96,108 | 4,734,129 bytes | 10,348,573 bytes |
| 16 (default) | 5,772 | 67,744 | 3,548,241 bytes | 9,162,685 bytes |
| 32 | 2,968 | 30,798 | 1,746,280 bytes | 7,360,724 bytes |

At 1 chunk per cell this world has more biome and cell pairs than the limit under
[Biomes](#biomes) allows, so it gets no biome layers there.

With the biome layers off (`biomes.enabled` `false`) the file is the 5,614,445 bytes of the
structures.

When the markers of a map are estimated at more than 10,000,000 bytes in `live/markers.json`, the
scanner logs a warning with the settings that make them smaller.

## Performance

- The scan runs on a thread called `bluemap-worldscan`, and with `scanThreads` above 1 also on
  `bluemap-worldscan-reader-N`. They are daemon threads at the lowest Java priority. **Java thread
  priorities have no effect on Linux** (HotSpot ignores them by default), so on Linux
  `maxChunksPerSecond` is what limits the CPU and disk use of a scan, and with `0` nothing does.
  Lower it if the game server's tick time rises during the first scan.
- The rate cap counts only chunks that are read. At the default of 500 chunks per second, a first
  scan of 4.2 million chunks (4,178,459 chunks over three dimensions) takes about 2.3 hours. Later
  scans read only changed chunks. A chunk costs about 70 microseconds of CPU to read, most of it
  zlib, so the default cap uses a few percent of one core.
- With no cap (`maxChunksPerSecond` `0`), one thread reads about 10,000 chunks a second from a warm
  disk cache. With `scanThreads` above 1, as many region files are read at once; a 95,697-chunk world took 9.6 s on one
  thread, 5.1 s on two, 2.9 s on four and 1.8 s on eight. The cap holds over all the threads. Keep
  `scanThreads` at 1 inside a game server.
- The scan state is saved to the addon folder every 100 regions, at most once a minute, so a scan
  that is cancelled keeps the regions it finished and the next scan continues from them. Layers are stored only after a
  complete pass, so every stored generation is complete.
- When a scan is cancelled (server stop, reload), the layers that were stored before stay as they
  are.

## What the log shows

The addon logs through the Java logger with the prefix `[bluemap-worldscan]`. The lines reach
standard error on every platform. Look for:

- `scanning world <id> (<dimension folder>)` when a world's pass starts.
- `scanned <dimension folder>: read N, unchanged N, failed N, wrong position N, changed during
  read N, pre-1.13 N, unsupported compression N; DataVersions ...` at the end of each world's
  pass. The DataVersions are counted in six buckets: `< 1466`, `1466-2199`, `2200-2831`,
  `2832-2843`, `2844-2969` and `>= 2970`. At debug level every distinct DataVersion is listed
  too. Structure and biome ids the addon does not know are listed at the end of the line: the first
  20 of each kind, then how many more.
- `stored generation G of the layers of map <id> (N markers)` when new layers were stored, or
  `the layers of map <id> are unchanged` when this instance stored these very layers before.
- `built N biome layers of world <id> in S s` when the biome areas of a world were worked out.
  A warning before that line says when the biome layers of a world were skipped (too many cells,
  or too large; the line then says 0) or when a world has more than 512 biomes. When the biome
  layers could not be built at all, a warning replaces the line. The structure layers are stored in
  every case.
- `showing generation G of map <id> (N layers)` when an instance puts a stored generation on its
  map.

If the dimension folder of a world has no `region` folder (a wrong path, an unmounted volume), the
scan logs a warning, reads nothing and stores nothing, so it cannot wipe your layers.

## Old chunks

Chunks saved before Minecraft 1.13 are counted in the `pre-1.13` number of the scan line and
nothing else is read from them. BlueMap 5.29 cannot read them either. The `data/*.dat` structure
files of those versions are not read.

To convert them, run the Minecraft server with `--forceUpgrade` (back up the world first). It
rewrites old chunks in the current format and moves the old structure data into the chunks. A
chunk's save time decides whether it is read again, so afterwards create the `reset` file to be
sure the scan reads every chunk again.

## Privacy

BlueMap's webserver serves a map's asset storage to anyone who can reach the map. The addon puts
three things there, per map:

- `bluemap-worldscan-layers.json.gz`, the layers: the markers and biome areas of the layers that are
  built, with their positions and popups. This is what `live/markers.json` shows anyway. The biome
  areas outline every chunk whose biomes have been generated, at the resolution of
  `biomes.cellSizeChunks`, also outside a map's render bounds or mask.
- `bluemap-worldscan-manifest.json`: the format version, the generation number, the scanner id (a
  random UUID), the addon version and a SHA-1 of the layers.
- `bluemap-worldscan-icon-<layer>-<hash>.png`, the icons.

Anyone who can open the map can see the structure positions and the biome areas of the layers that
are built. With small cells the biome areas are close to the per-chunk biome data of the world.
If that is a problem for a structure layer, put it in `structures.disabledLayers`. `biomes.disabled`
hides single biomes; only `biomes.enabled` `false` removes the footprint of the explored world.

These stay with the scanning instance, in its addon folder, and are never put in the storage: the
scan state (the save time of every chunk, the structures of layers you disabled, the biomes of each
chunk exactly, not at the cell size of the biome layers), the config, the client jar and the
`scanner-id` file. The value in `scanner-id` is the
scanner id in the public manifest. Instances that do not scan read no world files and download
nothing.

## When a new release is needed

You need a new release of the addon when:

- BlueMap changes its API in a way that breaks the addon,
- Minecraft changes the chunk format so the addon cannot read structure starts any more, or
- a new Minecraft version adds structures or biomes. Until then a structure is shown in a layer
  named from its id, with no icon, and a biome in a layer named from its id, in a colour worked out
  from it. Both are listed as unknown in the log.

A stored layers file or manifest in a format newer than the running instance knows (release 1.1.0
stores layers in format version 2, which release 1.0.0 does not know) is left alone: the instance
keeps the layers it shows and logs `update bluemap-worldscan on this instance`. A
scanning instance stores nothing for a map whose storage holds a format newer than it knows, and
logs a warning, so an old addon never replaces the layers of a newer one.

## Build

```
./gradlew build
```

needs Java 25. The addon jar is `build/libs/bluemap-worldscan-<version>.jar`. The other jar in that
folder, `-plain`, is the build without its libraries and is not for use.

Pushing a tag that starts with `v` runs `.github/workflows/release.yml`. It builds the jar, checks
it and attaches it to a GitHub release.
